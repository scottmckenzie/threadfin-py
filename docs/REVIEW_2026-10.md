## Findings

### 1. Medium: passwords are stored with a fast, unsalted hash

`auth.py` `credential_hash`. Passwords are `HMAC-SHA256(key=password, msg="_remote_db")`: fast, with
no salt, so equal passwords give equal hashes. Backups contain `authentication.json`, so anyone with a
backup can try billions of guesses per second offline.

This is Go's exact format, kept so existing config folders work (see the `auth.py` docstring).

Fix: upgrade a user's hash at their next successful login. Store a `hashlib.scrypt` hash using the
per-user `_salt` (already in the file, never used) and check it first from then on. Trade-off: the Go
app could no longer log those users in.

### 2. Medium: no limit on failed logins

`ui.py` `login`, `api.py` `login` (`/api/v1/login`), the `login` command of Go's `/api/`, and every
Basic-auth (`/lineup.json`) and URL-credential (`/m3u/`, `/xmltv/`) check. Anyone who can reach the
server can try passwords as fast as it answers; with finding 1, weak passwords do not last.

Fix: count failures per client address and per username in `Authentication.authenticate` and refuse
for a while after about 5 failures.

### 3. Low: credentials can end up in logs

- `cli.py` `serve`: at `-debug 2` and up, uvicorn's access log records the full path, including
  `?username=…&password=…` on `/m3u/` and `/xmltv/`.
- `providers.py` `download`: error messages include the full provider URL, which for most IPTV
  providers holds the account password (`get.php?username=U&password=P`). The message reaches the
  Log page, `/api/v1/log` and the build report.

Fix: blank out credential query parameters when building error messages, and filter the access log
the same way.

### 4. Low: request bodies and backup entries have no size limit

`api.py` (`request.body()` in the JSON and upload helpers) and `backup.py` `restore_backup`
(`zf.read`). The 5 MB logo limit is checked only after the whole body is in memory, and a restore
unpacks each zip entry fully in memory, so a small zip that expands hugely can exhaust memory.

Needs a logged-in user, or web login switched off (then anyone on the network has full control
anyway), so the real exposure is small.

Fix: refuse requests whose `Content-Length` is over a cap; check `ZipInfo.file_size` before each
`zf.read`.

### 5. Low: playlists can make the server fetch local-network addresses

`imagecache.py` `ImageCache._download`. With `cache.images` on, every logo URL in a provider's
playlist is downloaded, including private addresses (a router, `169.254.169.254`). The response is
kept only if it is a real image, so this is limited to blind GET requests. Go did the same.

Fix (optional): resolve the host and skip private and loopback addresses for logo downloads.

### 6. Low: adding a provider skips the build lock

`service.py` `add_provider` and `providers.py` `ProviderManager.add`. The `service.py` docstring
says changes happen under the build lock, but `add` puts the new record into the shared
`settings.files` before downloading, without that lock. A build running at that moment reports a
temporary "Local copy of the file no longer exists" error for the new provider.

Fix: download first, then add the record under the lock (`Service._locked`), or have the build skip
providers that have no local copy yet.

### 7. Low: strict mypy fails (23 errors), including dead fields

- `BuildReport.created` is declared `int` but is assigned a list of ids in `Service._build`; neither
  it nor `removed` is read anywhere. Use `len(result.created)` or remove both.
- `epg.py` `write_xmltv` uses `target` for a channel in a loop and later for the output path
  (4 of the errors).
- The rest: missing annotations, `list` vs `Sequence`, `Any` returns.

Fix: clear them, then add `uv run mypy src` to the checks in `CLAUDE.md`.

### 8. Medium: a backup restore could plant a program that the channel probe runs (fixed)

Found by the security review of `main` at `6329987`. `backup.py` `restore_backup` kept each archive
entry's execute bit (`_mode`) and applies the archive's `settings.json`, which only gets schema
validation (the settings page's "must be an existing file" check for `ffmpeg.path` is skipped).
`probe.py` `resolve_ffprobe` prefers an `ffprobe` file next to `ffmpeg.path`, without checking the
folder, and the channel probe runs it. So anyone who can use the UI or REST API (any host on the
network while web login is off) could restore a zip with `"ffmpeg.path": "<config>/x/ffmpeg"` and an
executable `x/ffprobe`, then probe a channel to run it as the service user (after a restart if a
probe had already run). Restore is the only way to plant an executable: logo uploads are written
0644 and providers are URLs.

Done in `227558e`: restored files keep only their read/write bits (`mode & 0o644`;
`authentication.json` stays 0600). The Go golden case `restore_executable_mode` is now a listed
divergence. A planted non-executable `ffprobe` now only makes the probe fail ("failed to execute
ffprobe").

Optional defence in depth, not done: check `ffmpeg.path` / `vlc.path` from a restored `settings.json`
as the settings page does, refuse an ffprobe inside the config folder, and reset the cached ffprobe
path in `Service.reload()`.

## Performance

Measured on the review commit (Python 3.12). P1–P3 are worth doing; P4 and P5 are small.

### P1. High: the whole guide file is parsed for every live-event channel

`xmltv.py` `count_programmes`, called through `make_program_counter` from `xepg.py`
`update_database` (lines 425, 433, 489). During matching, each live-event channel asks how many
programmes its guide has, and each call streams through the entire XMLTV file again; nothing is
cached. One call on a 28 MB guide took 0.30 s. Full guides are often 100–300 MB (1–3 s per call),
and a channel can be asked twice, so 100 live channels mapped to a real guide cost minutes per
build. Channels mapped to the built-in PPV guide are not affected.

Fix: in `make_program_counter`, read each file once and count every channel in that pass
(`Counter` of the `channel` attribute, keyed by file). The counter is created for each build, so the
cache cannot go stale; an unreadable file still counts 0.

Done in `6097d82`: 50 live channels mapped to the 28 MB guide went from 15.3 s (50 parses) to
0.33 s (1 parse). `count_programmes` is replaced by `programme_counts`, which counts every channel of
a file in one pass; tests in `tests/test_xmltv.py`.

### P2. Medium: channel matching is quadratic in the number of new streams

`xepg.py` `update_database`. A first build took 0.05 s for 1,000 new streams, 0.09 s for 2,000,
0.32 s for 4,000 and 1.26 s for 8,000 (about 8 s for 20,000). The time splits roughly evenly between:

- the UUID fallback: a stream without an exact match scans every known channel for a UUID match,
  including channels created earlier in the same loop;
- `free_number`: each new channel counts up from its group's starting number past every number
  already taken.

Fix, with the same results: index known channels by `(file_m3u_id, uuid_value)` with `setdefault`
(keeps the first match, as the scan does) and add each new channel to it; give `free_number` a
cursor per starting number (every number below the cursor is already used, and the used set only
grows).

### P3. Medium: parsing a guide keeps every element in memory

`xmltv.py` `iter_top_level`, used for the guide channel list, programme counts and writing the
guide. Each element is cleared after use, but the root `<tv>` still holds every emptied child, about
80 bytes each: peak 13.8 MB on the 28 MB test guide, about 150 MB for a 300 MB guide, on every pass.

Fix: keep the root from the first `start` event and `root.remove(element)` after the yield (the
element is then always the root's only child, so this is O(1)). Peak on the test guide: 0.2 MB.

### P4. Low: backup-channel lookup scans every stream

`xepg.py` `map_channels`: every backup name set on a channel is compared with every stream
(backups × streams). Fix: build `{stream name: BackupStream}` once with a dict comprehension (later
streams overwrite earlier ones, so the last match still wins).

### P5. Low: `/lineup.json` rewrites `urls.json` on every request

`service.py` `Service.lineup` calls `StreamRegistry.save` on every request; Plex polls it. At 5,000
channels that is 17 ms and 1.4 MB written per poll, even when nothing changed. It also runs outside
the build lock, so a poll overlapping a build can briefly put stale stream ids back (the next build
removes them).

Fix: have `StreamRegistry.add` note whether an entry is new or changed, and save only then.

Apart from P5, the only concurrency issue found is finding 6.

## Maintainability notes

- 13 of 478 functions are over 50 lines. The one worth splitting is `xepg.py` `update_database`
  (186 lines, about 42 branches); the 69 Go golden cases make that refactor safe. The `routes()`
  factories in `ui.py` and `api.py` only look long because they hold many small handlers.

## Checked and found sound

- Every web UI and API route checks CSRF first, then the session (`ui.py` `page`, `api.py`
  `guarded`). A POST needs a header a cross-site form cannot send, or a JSON body.
- The session cookie is `HttpOnly`, `SameSite=Lax`, and `Secure` on HTTPS.
- Backup restore validates the whole archive before writing, and refuses entries outside the config
  folder.
- Uploaded logo and cached image names are strictly validated; SVGs are served with a
  Content-Security-Policy that blocks scripts.
- Downloads are http/https only, with a total deadline and a size limit; ffprobe is limited to an
  allowlist of protocols.
- `settings.json` writes are atomic and serialise a snapshot, so concurrent saves cannot corrupt it.
- No leaked file handles or threads; the session tokens, log buffer and failed-image list are all
  bounded.
